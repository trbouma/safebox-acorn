# Acorn Recovery Specification

## Summary

Acorn wallet recovery requires enough information to derive or restore the
wallet key and locate the encrypted wallet events. The practical recovery
bundle is one of:

```text
home_relay
offline_mnemonic

or

home_relay
nsec
```

For wallets generated by Acorn, or initialized from external entropy, the
original offline mnemonic and its derived `nsec` are alternative recovery
secrets.

Wallets initialized from an existing `nsec` do not have an Acorn-generated
offline mnemonic. Anyone with either valid secret can control the wallet if
they can access the wallet's relay-backed data.

Restoring the keypair restores the cryptographic continuity and authority of
the Acorn component or wallet lineage. It does not restore or prove the civil,
legal, or social identity of a person. Human identity is interpreted outside
Acorn from claims and context such as NIP-05, kind `0` profiles, Lightning
addresses, credentials, relationships, and legal records.

## Recovery material

### `home_relay`

The home relay is the relay where Acorn publishes and retrieves wallet state,
private records, proofs, and reserved records.

Example:

```text
wss://relay.getsafebox.app
```

The home relay is not secret, but it is required for practical recovery because
the wallet data is relay-backed.

### Offline mnemonic

An **offline mnemonic** is the original BIP39 mnemonic produced from wallet
entropy during initialization. It is displayed for secure offline backup and
deterministically derives the operational `nsec` using SLIP-10 secp256k1.

For wallets generated by Acorn, the offline mnemonic is currently 12 words.
For wallets initialized with `acorn init --entropy`, it is a 24-word BIP39
mnemonic encoding the supplied 256 bits plus the BIP39 checksum.

The offline mnemonic is bootstrap and recovery material, not ordinary wallet
state. The target security contract is:

- display it only during wallet creation through an explicit sensitive-output
  flow;
- require the operator to record and verify an offline backup before funding;
- do not retain it in local configuration, relay-backed records, logs, or
  routine command output; and
- use the derived `nsec` as the operational secret of the running component.

Once initialization ends, Acorn cannot reconstruct the original offline
mnemonic from the `nsec`. The `nsec` contains the final private key, not the
original entropy, BIP39 seed, derivation context, or mnemonic checksum.

Wallets initialized from an existing `nsec` do not have an Acorn-generated
offline mnemonic. Acorn reports it as unavailable rather than manufacturing a
new mnemonic from the private-key bytes. Such a mnemonic would not be the
original phrase and normal BIP39 derivation would not reproduce the imported
key. The imported `nsec` itself must be backed up.

Example format:

```text
word1 word2 word3 ...
```

During recovery, the offline mnemonic is entered once at a hidden prompt.
BIP39 checksum validation detects an invalid mnemonic without requiring the
user to enter all 12 or 24 words twice:

```sh
acorn recover --homerelay <home relay>
```

### External entropy

External entropy is a wallet-creation input, not an additional runtime secret.
Acorn accepts exactly 32 bytes encoded as 64 hexadecimal characters through a
hidden, confirmed prompt:

```sh
acorn init --entropy
```

Acorn does not hash the value again. It converts the bytes into a 24-word
English BIP39 phrase and then follows the standard Acorn phrase-to-`nsec`
derivation. The raw hexadecimal input is not written to local configuration or
wallet metadata. Under the target offline-mnemonic policy, the equivalent
mnemonic is displayed during initialization and is not retained afterward.

The offline mnemonic, external entropy, and resulting `nsec` represent
equivalent control over the wallet and must receive the same protection. See
[External Entropy Initialization](EXTERNAL-ENTROPY-INITIALIZATION.md).

### Implementation status and migration

Current Acorn wallet metadata may retain the generated mnemonic in encrypted
relay-backed state, and `acorn set --show-recovery` may redisplay it. This is a
known gap against the target offline-mnemonic policy above, not the desired
long-term contract.

Before stable release, Acorn should stop writing newly generated mnemonics to
wallet metadata, remove the expectation that they can be redisplayed later,
and provide a deliberate migration that removes retained mnemonic fields from
existing wallet state. Until that migration is implemented and verified,
operators must assume that an existing wallet's encrypted relay events may
contain its mnemonic.

### `nsec`

The `nsec` is the Nostr private key encoding used directly by Acorn.

Example format:

```text
nsec1...
```

The `nsec` is often the easiest value to paste into configuration, but it is
also the most direct private-key material. Treat it like a wallet seed.

## Showing recovery information

The CLI exposes a recovery display command:

```sh
acorn set --show-recovery
```

Because this displays sensitive material, the command must ask for confirmation
before printing anything:

```text
Sensitive recovery material will be displayed. Continue? [y/N]:
```

Ordinary `profile`, `recover`, `init --force`, and `init --json` output must not
include the offline mnemonic or `nsec`. Automated initialization may include
newly generated recovery fields only during the creating invocation, when the
caller explicitly supplies `--json --include-recovery` and accepts
responsibility for protecting captured output.

Under the target offline-mnemonic policy, a later recovery display can print
the home relay and operational `nsec`, but it cannot print the original
mnemonic because Acorn no longer retains it:

```text
home_relay: wss://relay.getsafebox.app
offline_mnemonic: unavailable (not retained after initialization)
nsec: nsec1...
```

The mnemonic is available only in the sensitive output presented during its
creation. Existing wallets may continue to show a retained phrase during the
migration period described above.

The command intentionally avoids printing unrelated profile details, private
hex keys, access keys, balances, or record contents.

## Recovery flow

To recover on a fresh machine:

1. Install Acorn.
2. Run `acorn recover` with the home relay and enter the offline mnemonic at
   the hidden prompt.
3. Acorn derives the `nsec`.
4. Acorn verifies that wallet data exists on the home relay.
5. Acorn writes the local minimal config.

Example:

```sh
acorn recover --homerelay relay.getsafebox.app
```

Relay names are normalized so a bare relay hostname becomes:

```text
wss://relay.getsafebox.app
```

## Minimal local config after recovery

The local CLI config should only need:

```yaml
nsec: nsec1...
home_relay: wss://relay.getsafebox.app
```

Additional preferences should be stored in encrypted records where possible,
not as plaintext local config.

## Security considerations

- Do not paste recovery output into chats, logs, issue trackers, screenshots, or
  terminal transcripts that may be retained.
- Never put an offline mnemonic or `nsec` directly in a command argument or
  environment variable. Shell history, process inspection, crash reporting,
  and diagnostics can retain those values.
- For automation, use `--seed-file` with an owner-only (`0600`) regular file,
  or use `--seed-file - --yes` and provide the phrase on stdin.
- Do not run `--show-recovery` in a shared screen session.
- Prefer writing recovery material to an offline password manager or physical
  backup.
- The `home_relay` is not sufficient to control the wallet, but the offline
  mnemonic or `nsec` is.
- If recovery material is exposed, assume wallet control may be compromised.
- Never derive external entropy by hashing a password or other guessable text.
- A hidden prompt prevents ordinary terminal echo but does not protect a
  compromised device, clipboard, or entropy generator.

## Open questions

- Whether Acorn should eventually support a machine-readable recovery export
  format.
- Whether `--show-recovery --json` should be supported.
- Whether recovery display should require typing a stronger confirmation phrase
  instead of a yes/no prompt.
